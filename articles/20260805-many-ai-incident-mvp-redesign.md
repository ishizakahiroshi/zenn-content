前の記事を公開したその日のうちに、作ろうとしていたCLIの仕様をかなり大きく書き直しました。

前回は、npmのサプライチェーン侵害を調べたときに「いつinstallしたか」が分からず、取り込み履歴を残す `intakelog` を作ろうと思ったところまでを書いています。

https://qiita.com/ishizakahiroshi/items/333278757e8e93c64b9b

きっかけになったnpmのサプライチェーン攻撃については、姉妹記事で依存関係、`preinstall`、provenanceの観点からもう少し技術寄りに整理しました。

https://zenn.dev/ishizakahiroshi/articles/20260805-npm-chaindrop-attack

ところが実装計画をAIと壁打ちしてみたら、最初に出てきたMVP案が弱かった。技術的には筋が通っているのに、利用者が導入してもあまりうれしくない。ここを突き詰めた結果、単なる台帳CLIではなく、開発マシンの棚卸しからインシデント対応までをつなぐ `MANY-AI Incident` という製品へ変えることにしました。

:::message alert
この記事は、その設計変更の記録です。現時点では名前を予約して仕様を固めている段階です。以下のコマンドは完成後の想定で、公開済みの `0.0.1` は名前予約用のスタブです。
:::

## 結局、何を変えたのか

最初に考えていたのは、これから何かを入れるたびに1行記録する道具でした。

```text
date, kind, name, version, source, integrity, project, why, actor
```

これ自体は今も必要です。ただ、これだけではすでに開発環境ができあがっている人に何も返せません。導入した日から先の記録しかなく、過去から積み上がったパッケージ、CLI、リポジトリは空白のままです。

そこでv0.1の約束を、次の一周が終わるところまで広げました。

- 1コマンドで、現在のマシン全体を棚卸しする
- パッケージがどのリポジトリで使われているかを結び付ける
- 取得できなかった対象を「異常なし」に混ぜず、件数と理由を出す
- osv-scannerの結果を、影響するリポジトリまで含めて表示する
- 今後の導入は、時刻、取得元、理由、実行主体とともに記録する
- CLIとMCPから同じデータを返し、AIエージェントへ調査と修正を引き渡せるようにする

想定している入口はこうです。

```powershell
many-ai-incident scan C:\path\to\repos
many-ai-incident report
many-ai-incident mcp serve
```

名前は変わりましたが、append-onlyの内部台帳は `intakelog schema` として残します。製品名と内部データ契約を無理に同じ言葉へ寄せないことにしました。

## 最初のMVP案は、利用者ではなく実装者に都合がよかった

壁打ちの最初に出てきた案は、永続データの契約を先に固めるものでした。

パッケージ管理ツールのscan、既存状態のバックフィル、コマンドのラッパー、HTMLレポート、osv-scanner連携は後回し。まずappend-onlyのCSVを正しく書けるようにする。

実装順としては正しいです。内部マイルストーンなら、これでいい。

でも、これを `v0.1.0` として利用者に渡したらどうなるか。インストールして、空の台帳ができて、手入力で1行追加できる。それだけです。

「これを除外したら、利用者は何もうれしくないよね」と指摘されました。

その通りでした。少し刺さった。

MVPを「最小の実装」と考えすぎていて、「最小でも価値が一周する製品」になっていなかったのです。scanやレポートをv0.2、v0.3へ逃がせば、興味を持って試した人はv0.1の時点で離れます。次の版まで待ってくれる前提がおかしい。

なので実装量を増やしました。公開するv0.1は小さな内部基盤ではなく、初回の棚卸しからHTMLを開くところまで完成させます。途中成果は内部マイルストーンかprereleaseとして刻み、利用者には出しません。

![](/images/2026-08-05_many-ai-incident-mvp-redesign_illustration-control-room.png)

最初は一冊の帳面を作ろうとしていました。壁打ち後は、その帳面を事実の土台にしつつ、棚卸し、確認、対応まで見渡す管制盤を作る形に変わっています。

## すでに大量に入っている人を、初日に置き去りにしない

いちばん大きかった問いは、「すでにいっぱい入れちゃってる人にはどうするのか」でした。

未来のinstallだけを記録しても、今日のマシンに何があるか分からなければ、インシデント対応には使えません。だから `scan` は付加機能ではなく、最初の入口にしました。

対象はnpmだけではありません。npm、pnpm、Bun、Scoop、winget、pip、Cargo、Go、Gitリポジトリを横断します。ソースツリーでは、osv-scannerが対応するlockfileやmanifestを探します。

ただし、過去の導入日時をファイルの更新時刻から作ることはしません。ここは前回の反省を曲げない部分です。

データを2種類に分けます。

- `events`: `run` や `record` を通して、取得時刻を事実として確定できた記録
- `observations`: `scan` した時点で、その名前とバージョンが存在したという記録

観測時刻を取得時刻へコピーしない。分からないものは空欄にする。バックフィルは「過去の取得日時を復元する」のではなく、「今ここに存在するものを観測する」と定義し直しました。

これなら、既存ユーザーにも初日から棚卸しという価値を返しつつ、推測を事実の顔で保存せずに済みます。

## パッケージ名だけ並んでも、次の行動につながらない

HTMLの初期モックも、一度作ってから直しました。

最初の画面で導入価値はだいたい伝わる。でも、パッケージがどのリポジトリと紐づいているのか分かりにくい。ここが弱いと指摘されました。

たしかにインシデントが出たとき、知りたいのは「危険なパッケージが1件あります」だけではありません。

- どのリポジトリで使っているのか
- 直接依存なのか、推移依存なのか
- マシン共通のCLIなのか
- 所属を判断できないものなのか
- そのリポジトリは最後まで走査できたのか

ここまで分かって、ようやく修正に移れます。

そこで最初の画面は、マシン全体の棚卸しを主役にしました。リポジトリ所属、マシン共通、所属不明、未走査を分けて表示し、リポジトリからパッケージへも、パッケージから利用リポジトリへも辿れるようにします。

![](/images/2026-08-05_many-ai-incident-mvp-redesign_fig1.png)

図の中央にある台帳は、製品そのものではなく事実を揃える層です。現在の観測と確定した取得イベント、所属関係、未走査を分けたまま、HTML、CLI、MCPへ同じ意味で渡します。

## インシデント情報の取得先も、1本に固定しない

脆弱性の照合は、引き続きosv-scannerへ委譲します。自前の脆弱性データベースや判定ロジックは持ちません。

https://github.com/google/osv-scanner

一方で、インシデント情報の入口をOSVだけに焼き付けるのも避けます。OSVを標準の取得先にしつつ、ベンダーの公開情報や利用者が管理する情報源を設定で追加できるsource adapterに切り出します。

ネットワークへ勝手に依存情報を送ることはしません。オフラインDBを既定とし、更新や外部取得は明示操作にします。複数の取得先がある場合も、どの情報源が成功し、どれが失敗したかを残します。取得失敗を「該当なし」にはしません。

CLIではversion付きJSONを正本にし、MCP serverは同じデータを返します。AIエージェント専用の別形式を増やさず、調査対象、根拠、影響リポジトリ、未走査範囲をまとめて渡せる形にします。

AIへ自動修復を任せるわけではありません。修正候補と根拠を渡し、リポジトリ内のルールを読ませ、テストと再scanで確認するところまでを一つの流れにします。勝手に削除や更新をする機能はv0.1に入れません。

## TypeScriptをやめて、Goを主実装にした

前回の記事では、実行時依存を増やさないためにTypeScriptの標準ライブラリだけで書く、と書きました。ここも変えました。

対象が1ファイルの追記ではなく、巨大なディレクトリ走査、SHA-256、複数の外部CLI、timeout、Ctrl+C、HTML生成まで広がったからです。主実装はGoにして、OSとCPUごとのネイティブバイナリをnpmから配布します。

npmは入口として残します。薄いJavaScript dispatcherが、その環境用のバイナリを選んで起動するだけです。postinstallで外部URLから実行ファイルを取る方式にはしません。

Rustも候補に残しましたが、この処理はCPU計算よりファイルI/Oと外部CLI待ちが中心です。まずGoとRustで小さな走査coreを同じfixtureに当て、起動時間、走査時間、メモリ、キャンセル、配布の再現性を測ります。Goが目標を満たせなければ、公開APIを固定する前にRustへ切り替えます。

言語を先に信仰しない。利用者が速い、軽い、入れやすいと感じるほうにします。

## 名前も、作ろうとしているものに合わせて変えた

`intakelog` は、取り込み履歴を記録する道具としては合っていました。でも、マシン全体を棚卸しし、インシデント情報と照合し、影響するリポジトリをAIエージェントへ渡すところまで広げると、製品名としては狭すぎます。

最終的に、名前はこう整理しました。

```text
製品名:     MANY-AI Incident
package:    many-ai-incident
CLI:        many-ai-incident
MCP server: many-ai-incident mcp serve
内部台帳:   intakelog schema
```

npmでは `many-ai-incident@0.0.1` を予約済みです。ただし、これは名前を確保するための最小スタブで、まだ製品として使える版ではありません。

https://www.npmjs.com/package/many-ai-incident

GitHubリポジトリは現在のURLを維持したまま、製品名に合わせて改名する予定です。削除して作り直さず、履歴を残したまま名前だけ変えます。

https://github.com/ishizakahiroshi/intakelog

## v0.1を大きくする代わりに、何を捨てるか

何でも入れるわけではありません。v0.1で完成させるのは、導入直後の棚卸しから、インシデント時の確認、今後の記録までの一周です。

外すのは、最初の価値に直結しないものです。

- 常駐デーモンと定期実行
- Git hookやshell profileの自動書き換え
- 自動削除、自動更新、lockfileの修正
- GUI、Webサーバー、クラウド同期、SaaS
- 独自の脆弱性DB
- 過去のshell履歴やmtimeから導入日時を推測する処理
- 台帳の既存行を編集、削除、並べ替える機能

ここは増やさない。逆に、scan、HTMLレポート、osv-scanner連携、主要な取り込み経路は「後で」へ逃がしません。

## おわりに

最初の案より、実装量はかなり増えました。たぶん時間もかかります。

でも、空の台帳を渡して「将来役に立ちます」と言うより、初日に自分のマシンが見えるほうがいい。v0.1で離れた人に、v0.3の良さは届きません。

まだ設計を固めたところです。次はGoとRustの小さな走査coreを比べ、HTMLまで通る最初の縦切りを作ります。小さく作るのは公開範囲ではなく、内部の実装順にします。

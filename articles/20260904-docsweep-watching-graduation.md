## 直した直後に「完了」にしない。でも寝かせっぱなしにもしない

![様子見の卒業期限のヒーロー](/images/2026-09-04_docsweep-watching_hero.png)

![記事の要約](/images/2026-09-04_docsweep-watching_infographic.png)

自作で [docsweep](https://github.com/ishizakahiroshi/docsweep) という CLI を作っています。AI が量産する作業ログ Markdown を、腐らせず自動で片付ける道具です。

- 何ができるかの紹介ページ: https://ishizakahiroshi.com/work.html?id=docsweep
- リポジトリ（Star をいただけると励みになります）: https://github.com/ishizakahiroshi/docsweep

同じ悩みを持っている方は、下記で入ります。

```bash
pip install docsweep
pip install 'docsweep[all]'   # Web UI・対話レビュー・MCP まで使う場合
```

入れたら 1 回だけ `python -m docsweep init` を実行します。設定は全 OS 共通で `~/.docsweep/` に置かれます。

起動後の見え方は OS で違います。

Windows は `python -m docsweep triage` や `python -m docsweep serve --root <スキャンしたいフォルダ>` で起動します。`serve` は `127.0.0.1` で待ち受けるので、止めるときはそのターミナルで Ctrl+C です。

macOS と Linux は `python3 -m docsweep triage` / `python3 -m docsweep serve --root ~/dev` です。macOS の system Python に PEP 668 の保護がかかっている場合は `--user` か venv 経由でインストールしてください。

**PATH に `docsweep` を通す必要はありません。** `python -m docsweep ...` で全機能に届きます。これは意図的な設計で、`docsweep` という短縮形は Scripts/bin が PATH に入っている人向けのおまけです。

最初にやることは `python -m docsweep brief` です。何も思い出せない状態でも、今日やる 1 件を断定して返します。

この話には前があります。docsweep を PyPI に初リリースしたときの記事の続きです。

前回の記事: [AIが毎日量産するplan_*.mdを腐らせない。docsweepをPyPIに初リリースした](https://zenn.dev/ishizakahiroshi/articles/20260703-docsweep-first-release)

## 「直したのに、まだ完了にできない」の置き場所がなかった

バグを直した直後の状態って、微妙です。

コードは直った。テストも通った。でも「本当に直ったか」はまだ分からない。同じ症状がもう一度出るかもしれないし、直した副作用が別のところに出るかもしれない。

ここで作業メモを `[完了]` にすると、archive へ移送されて視界から消えます。再発したときに「そういえば前に似たのを直した気がする」から探し直すことになる。かといって `[実行中]` のまま置くと、今日やることの一覧に毎朝出てきて邪魔になります。

docsweep はこのために `[様子見]` という状態を持っていました。直し終えて寝かせている、という意味です。`sweep`（自動移送）は様子見を対象にしません。寝かせているものを勝手に片付けないのが不変条件です。

で、これがうまくいきませんでした。

![様子見の棚に作業メモが積み上がっている様子](/images/2026-09-04_docsweep-watching_illust1.jpg)

守られすぎたんです。様子見に入れたら最後、誰も取り出さない。自分のリポジトリを数えたら、様子見のまま 3 週間放置されているものが 2 本、2 週間が 1 本ありました。archive 直下には版の区別なく 73 本が平置きされていて、どれがいつ終わったのかも分からない。

「寝かせる」は実装できていたけど、「起こす」がなかった。

## due を「締切」ではなく「起こす合図」として使う

docsweep には元々 `due`（期日）という第 2 軸があります。ラベル（状態）が第 1 軸で、due が第 2 軸。

最初に考えたのは「due が来たら自動で archive へ送る」でした。これはすぐ捨てました。

期日が来ただけで完了扱いにするのは、docsweep が解こうとしている問題そのものだからです。中身を見ないまま片付けたら、「AI が書いたメモが溜まって腐る」を「AI が書いたメモが確認されないまま消える」に置き換えただけになる。

なので、due の意味を状態ごとに変えることにしました。

- `[実行中]` の due = 締切。過ぎたら「やり忘れ」として赤く出す
- `[様子見]` の due = **卒業判定日**。過ぎたら「そろそろ見直す時期」として出す。ただし何も起きない

![状態の一本道と、due という第 2 の軸](/images/2026-09-04_docsweep-watching_fig1.png)

上の図のとおり、状態は保留 → 計画 → 実行中 → 様子見 → 完了の一本道で、廃止だけがどの可動状態からも分岐します。due はその上に重なる別の軸で、状態を進める力は持ちません。

一本道といっても**遷移を強制はしません**。実行中から直接 `[完了]` にもできますし、再発したら `[様子見]` から `[実行中]` へ戻せます。docsweep が固く守るのは「様子見は自動移送しない」の 1 点だけで、そこ以外は運用する人が決めます。

`[様子見]` へ移した瞬間に、その日から既定 3 日後の日付が `due` に入ります。3 日にしたのは、自分の運用で「再発するなら翌営業日までにはだいたい出る」という感覚があったからです。根拠は経験則で、統計を取ったわけではありません。プロジェクトごとに `.docsweep.yaml` で変えられます。

```yaml
due:
  default_offset_days:
    plan_watching: 3
    bugfix_watching: 3
```

## 昇格は明示操作でだけ起きる

卒業期限が来た文書を片付けるコマンドはこれです。

```bash
python -m docsweep promote --due-expired --dry-run   # 対象を下見する
python -m docsweep promote --due-expired             # 昇格して archive へ移す
```

`--due-expired` を付けたときだけ、「due 到来（当日を含む）かつ `[様子見]`」に絞り込まれます。due が無いもの、未来の due、`docsweep_policy: never_archive` を付けたものは動きません。

ここで意識的に踏ん張ったのが、**下見を先に出す**という点です。

`--due-expired` を付けない `promote` は様子見が全部対象になります。実装当初、下見の案内文だけ `--due-expired` を落としてしまっていて、「下見では 3 件と言っていたのに本実行で 30 件出た」という事故が起きかけました。下見と本実行で絞り込み条件が違うと、確認の意味がなくなります。

MCP からも同じことができます。

```
promote(due_expired_only=True, dry_run=True)
```

CLI のフラグ名は `--due-expired`、MCP の引数名は `due_expired_only` で綴りが違います。これは今回のリリース準備でドキュメントを読み返していて気づきました。どの文書にも書かれていなかったので、AI エージェント向けのガイドに追記しました。

![下見してから片付ける流れ](/images/2026-09-04_docsweep-watching_illust2.jpg)

## 1 本だけ長く寝かせたいときのための逃げ道

既定 3 日は設定で変えられますが、「この 1 本だけ 5 日寝かせたい」のために設定ファイルを書き換えるのは筋が悪い。

なので、その状態遷移にだけ効く上書きを付けました。

```bash
python -m docsweep apply --path <plan-or-bugfix.md> \
  --action relabel --to watching --watching-days 5
```

MCP なら `apply(..., action="relabel", to="watching", watching_days=5)` です。設定ファイルは変わりません。

既に `[様子見]` の文書に対してもう一度指定した場合は、**既存の due を保護します**。これは意図的で、様子見の再指定で期限が延びていくと、いつまでも卒業しない文書が作れてしまうからです。

## 実際に自分に効いた

昨日、この機能を実装した plan 自体が様子見に落ちました。

```
# [様子見] watching-graduate-after-days
due: 2026-09-06
```

自作の機能が自分自身に初めて適用された瞬間で、少し変な気持ちでした。9 月 6 日に卒業判定が来ます。そこで完了にするかどうかは、そのとき考えます。

あわせて、溜まっていた様子見 7 本を片付けました。archive の平置き 73 本も版ごとに分け直して、`archive/` 直下は空になりました。**73 本の仕分けで一番困ったのは、移送日が分からないことでした。** `shutil.move` も `mv` も mtime を保存するので、archive にあるファイルの更新日時は「最後に本文を編集した日」であって「片付けた日」ではない。結局、各リリースの作業記録を読んで振り分けました。

移送日を残す設計にするかどうかは、まだ決めていません。保留として起票だけしてあります。

## リリース直前に、目玉機能が CHANGELOG から抜けているのを見つけた

これは設計の話ではなく、単なる失敗談です。

実装のコミットメッセージは `feat: add due-based watching graduation` でした。そのコミットは CHANGELOG も 23 行足していました。だから当然、書いてあると思っていた。

リリース準備で `Unreleased` を版の節へ統合していて、内容を読んで固まりました。書かれていた 3 項目は、closeout チェックの緩和・必須セクションの明文化・配布フックの修正。**様子見卒業の話が 1 行もない。**

コミットメッセージと、そのコミットが CHANGELOG に書いた内容が、別のことを指していたわけです。テストは 1026 件全部通っていました。CHANGELOG の中身を検査するものが 1 つも無かったので、当然です。

これは検査を書くべきものとして残しました。文章で「気をつける」と書いても、次に同じことをやります。

## 学んだこと

- **「守る」を実装したら、同じ強さで「起こす」も実装する。** 片方だけだと、守られたものが永久に取り残される
- **期日を状態変更のトリガーにしない。** 期日は「見直す時期が来た」の合図まで。実際に動かすのは人か、人が明示した AI の操作
- **下見コマンドと本実行コマンドで、絞り込み条件を必ず揃える。** ここがずれると確認が確認にならない
- **コミットメッセージと CHANGELOG の中身は別物。** メッセージが `feat:` でも、書かれた内容がその機能とは限らない

## docsweep はこんなときに刺さります

- AI が書いた plan や bugfix が溜まって、どれが現役なのか分からなくなっている人
- 古くなったドキュメントを「要判断」として洗い出したい人
- 複数リポジトリの残作業を 1 画面で見渡したい人
- 直した直後の作業メモを、消すでも放置でもない形で置いておきたい人

いずれかに心当たりがあれば、`pip install docsweep` と `python -m docsweep init` の 2 コマンドで試せます。設定ファイルを手で書く必要はありません。

## おわりに

「寝かせる」を実装したときは、それで完成したつもりでいました。実際には半分しか作っていなかった。

守る仕組みを入れたら、そのぶん取り出す仕組みも要る。当たり前のことなんですが、守るほうは作っていて気持ちがいいので、そこで手が止まりやすいのだと思います。

3 日が適切な長さなのかは、正直まだ分かりません。しばらく自分で回して、長すぎたら縮めます。小さく。

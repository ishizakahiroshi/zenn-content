Dドライブの空き容量を見たら、9.9GBしか残っていませんでした。

正直、ぎょっとしました。何かのログが暴走したのか、変なファイルをダウンロードしっぱなしにしていたのか。掘る前は、そのどちらかだろうと思っていました。

:::message
結論から書くと、犯人はほぼ全部「ビルドキャッシュ」でした。Rust の target、Go の build/module cache、pnpm の store。合計で50GB近く。しかもどれも消して実害のないものでした。
:::

## 掘ってみたら、犯人は全部「作り直せるもの」だった

フォルダサイズを上から順に見ていくと、開発フォルダの中の複数の Rust プロジェクトが持つ target ディレクトリが軒並み数GBから十数GBありました。加えて Go の GOCACHE と GOMODCACHE、pnpm のグローバル store。

中身を見ればすぐ分かるんですが、全部「もう一度ビルドすれば作り直せるもの」です。ソースコードでも設定でもありません。

正直、見た瞬間は rm -rf したくなりました。数GBのフォルダがずらっと並んでいると、まとめて消したい衝動に駆られます。

## rm -rf ではなく、各ツールの「公式クリーン」だけを使う

ただ、ここで一度立ち止まりました。target と一口に言っても、中に何が混ざっているか自分では完全には把握しきれていません。ビルド中の一時ファイルなのか、キャッシュされた依存物なのか、それとも何か別の理由で置かれているものなのか。

自分で「これは消していい」と判定するロジックを書くより、各ツール自身に判定を任せる方が安全です。

- `go clean -cache` / `go clean -modcache`
- `pnpm store prune`
- 各リポジトリで `cargo clean`

これだけです。全部そのツールの開発元が「安全に消せる」と保証しているコマンドで、自作の削除ロジックは一切書きません。

実行してみたら、Dドライブの使用量は 84.1GB から 37.0GB まで落ちました。空きは 9.9GB から 57.0GB です。

![](/images/02_2026-09-27_dev-cache-cleanup_illustration-cleanup.png)

## 「月1でやった方がいいのかな」から始まったスクリプト化

一通り消して満足していたところ、ふと気づきました。多分これ、また同じだけ溜まります。Rust のプロジェクトを何本も並行して触っている以上、target は勝手に育ちます。

「月1くらいで手動でやるか」とも思ったんですが、絶対に忘れる自信がありました。なので、同じ手順をスクリプトにしておくことにしました。

安全側に倒すために、次の3つだけルールを決めました。

1. 削除は必ず各ツール公式のコマンド経由。自作のパス削除はしない
2. cargo の対象は「決めた走査ルートの中で、Cargo.toml が直下にあるフォルダの target」だけ。シンボリックリンクやジャンクションの先には潜らない
3. 既定は一覧表示だけの dry-run。実際に消すには明示のオプションが要る

:::message alert
2番目の「シンボリックリンクの先に潜らない」は地味に効きます。開発フォルダの中にはクラウド同期用のジャンクションが混ざっていることがあり、そこを踏むとキャッシュ以外のファイルまで走査対象に入りかねません。
:::

dry-run で試したところ、狙った target と store だけが一覧に出て、同期フォルダ側は一件も出てきませんでした。ここでようやく安心して `-Apply` を叩けます。

## 忘れっぽさへの対策は、道具じゃなくて索引だった

スクリプトを作ったところで、正直また存在を忘れる自信がありました。実際、作った直後に「これ絶対また忘れるな」と思いました。

対策として、手元に前から持っていた「道具一覧」の索引に1行追記しました。真新しい仕組みを作るのではなく、既にある一覧に載せる。それだけで、次に「Dドライブ整理どうやったっけ」となったときに見つけられます。

新しい道具を作ったら、その一覧に足す。地味ですが、これが一番効きました。

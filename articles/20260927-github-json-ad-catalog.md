![広告の更新をアプリのデプロイから分ける](/images/01_2026-09-27_github-json-ad-catalog_hero.png)

広告の商品を差し替えるたびに、アプリ全体を再デプロイする必要があるのか。学校を探す個人開発のWebアプリで、県別の問題集を紹介することになり、広告データをJSONとしてGitHubの別ブランチへ分けました。Cloudflare Pagesで動くアプリが、必要な県のファイルだけを実行時に読みます。

最初は群馬県だけでした。全国へ広げるときに欲しかったのは、「群馬県の学校なら群馬県の問題集、北海道なら北海道の問題集」という動きです。それに、来年版への入れ替えも、アプリのリリース作業から切り離したかった。

題材は、通える高校を地図で見ながら、親子で決める「manabi-map」です。[Webアプリ](https://manabi-map.app)で学校を選ぶと詳細を見られます。[GitHub](https://github.com/ishizakahiroshi/manabi-map)でソースを公開していて、概要は[作品紹介](https://ishizakahiroshi.com/work.html?id=manabi-map)にまとめています。

![アプリ、広告JSON、県ごとの表示を分ける設計の全体像](/images/02_2026-09-27_github-json-ad-catalog_infographic.png)

## JSONにするだけでは、デプロイから離れられない

最初に決めたのは、商品名や購入先をコンポーネントへ直接書かないことです。ここまでは普通の外出しです。

ただ、JSONをアプリの`public/`に置いて、アプリと一緒に配るだけでは、商品を変更したときにデプロイが必要です。ビルド時にJSONをimportしても、成果物へ取り込むタイミングは変わりません。

分けたかったのはファイルの置き場所だけではなく、**更新が利用者へ届く経路**でした。

広告は利用者に見せる公開情報です。商品名、紹介文、公開用の購入リンクを配るために、新しく非公開ストレージや管理APIを用意する必要はありません。そこで今回は、既に使っているGitHubに、小さな公開JSONを置くことにしました。APIの秘密鍵や利用者情報は、このJSONには含めません。

R2などのオブジェクトストレージも候補にはなります。ただ、今回の条件は「小さな県別ファイル」「差し替えは随時」「編集履歴を残したい」。まずはGitで変更履歴も確認できる構成にしています。

## アプリ用と広告用で、ブランチの役割を分ける

同じリポジトリに、アプリとは履歴を共有しない`book-ads`ブランチを用意しました。いわゆるorphanブランチです。ここには配信するJSONだけを置きます。

```text
main / develop                  book-ads
├ web/src/                      └ book-ads/
├ web/data/                        ├ 01.json  北海道
│  └ book-ads-source.json           ├ 10.json  群馬県
└ docs/                            └ …        都道府県別
```

`book-ads`は機能開発用のブランチではないので、`main`や`develop`へマージしません。広告の内容を編集して、このブランチへpushすること自体が配信更新になります。

アプリ側が持つのは、読み込み先の設定と、表示・検証の仕組みです。商品の中身は持ちません。設定例では、GitHub RawのURLにブランチ名を含めます。

```json
{
  "baseUrl": "https://raw.githubusercontent.com/OWNER/REPOSITORY/book-ads/book-ads"
}
```

上は説明用のURLです。`OWNER`と`REPOSITORY`を置き換え、末尾に`/10.json`を足せば群馬県のファイルを取得する、という形になります。コミットSHAに固定すると内容も固定されるため、ここでは更新対象のブランチを参照します。

もう一つ必要だったのが、Cloudflare Pagesのビルド設定です。広告用ブランチへのpushでもPreviewビルドが走るなら、「広告更新だけにしたつもり」でアプリのビルドを増やしてしまいます。

Productionは`main`のまま、Previewの対象から`book-ads`を除外しました。JSONの配信はGitHub Rawから行うので、このブランチでPagesを作る必要はありません。対象ブランチの指定方法は[Cloudflareの公式ドキュメント](https://developers.cloudflare.com/pages/configuration/branch-build-controls/)にあります。

![アプリのリリース経路と広告JSONの更新経路](/images/03_2026-09-27_github-json-ad-catalog_fig1.png)

アプリの変更はPagesへ、広告の変更はGitHub Rawへ届きます。この二つの経路を分けることで、商品だけを差し替えられます。

## 県を入力にして、必要なファイルだけ読む

表示の入力は、選択した学校の都道府県コードです。学校が広告の対象かどうかを確認し、対象ならその県のJSONを一つ取得します。

読み込み部分の入口は、次のようになります。これは要点だけの抜粋です。実装全体にはレスポンスの形式確認、読み取り中の容量制限、スキーマ検証もあります。

```ts
const response = await fetch(`${baseUrl}/${prefectureCode}.json`, {
  signal,
  cache: 'no-store',
  credentials: 'omit',
})
```

コードは[`bookAdSource.ts`](https://github.com/ishizakahiroshi/manabi-map/blob/v0.12.0/web/src/lib/bookAdSource.ts)にあります。公開JSONを読むだけなので、認証情報は送りません。県コードも、URLへ入れる前に検証します。

今回の対象は公立高校向けの問題集です。私立高校や、募集停止など対象外の状態では広告を出しません。「県が分かったら何でも出す」にはしない、という条件も表示側へ持たせました。

全国分をまとめたJSONではなく、県別にしたのは、北海道の学校を見ているときに他県の商品情報まで取得する必要がないからです。静的なHTMLを生成する段階では商品を埋め込まず、ブラウザで学校に対応するデータを取得してから表示します。

更新時には、対象県のJSONを編集し、検証してから`book-ads`へpushします。アプリの表示形式とスキーマが変わらなければ、商品名やリンクの差し替えのためにアプリのバージョンを上げたり、リリース用の文書を作り直したりする必要はありません。

リポジトリには、編集元JSONを検証して県別ファイルを生成するスクリプトも用意しました。次はリポジトリルートでの実行例です。出力先を指定しなければ検証だけで終わります。

```sh
node scripts/prepare-book-ads.ts catalog.json
node scripts/prepare-book-ads.ts catalog.json output
```

生成される`output/book-ads/`のうち、変更した県のファイルを広告ブランチへ反映します。このスクリプトはアップロードやアプリのビルドを行いません。

## 外部ファイルを、表示してよいデータに絞る

置き場所を外へ出すと、アプリを変えなくても内容が変わります。その便利さの分だけ、受け取ったものをそのまま画面に入れないようにしました。

JSONのバージョン、広告の有効・無効、項目の型、リンク先などを検証します。HTML形式の素材を扱う部分も、許可する要素や属性、URLを限定しています。任意のHTMLを流し込む仕組みにはしていません。

取得には5秒のタイムアウトを設け、本文は64KiBまでに制限しました。`Content-Length`だけではなく、ストリームを読みながらもサイズを数えています。これらの値と検証処理は、[公開している運用仕様](https://github.com/ishizakahiroshi/manabi-map/blob/v0.12.0/docs/reference_book-ad-catalog.md)とコードで確認できます。

配信先ごとの差もありました。GitHub RawはJSONファイルを`text/plain`として返すため、`application/json`だけを受け付けると正常なデータまで落としてしまいます。一方で、エラーのHTMLをJSONとして扱うことも避けたい。許可するContent-Typeを決めたうえで、最終的にはパースと内容の検証まで通します。

## 読めないときは、広告を出さない

![広告カードを外しても学校の情報はそのまま残る](/images/04_2026-09-27_github-json-ad-catalog_illustration1.png)

広告の取得に失敗したとき、前に取得した商品をいつまでも出し続けるかどうかも考えました。今回は、取得に失敗したら広告を消す方針です。学校情報の本文は、そのまま利用できます。

来年版へ切り替えたはずなのに古い商品が残ったり、停止したい広告がローカル保存から復活したりすると、運用が分かりにくくなります。古い広告やサンプル商品を代わりに表示する処理は入れていません。

ただし、**外部JSONにすれば即時反映になるわけではありません。**

ブラウザの再取得では`cache: 'no-store'`を指定していますが、配信側の共有キャッシュまで消せるわけではありません。検証時のGitHub Rawには`max-age=300`の応答がありました。アプリも表示中の定期取得やタブへ戻ったタイミングで確認するため、更新が見えるまでには間隔があります。再取得の条件も[運用仕様](https://github.com/ishizakahiroshi/manabi-map/blob/v0.12.0/docs/reference_book-ad-catalog.md)に記載しています。

「アプリの再デプロイが不要」と「全利用者の画面から今すぐ消せる」は別の要件です。厳密な即時停止が必要になれば、配信先やキャッシュ制御を見直すことになります。

## 全国へ広げてから、実際の経路を確かめた

全国の県別JSONを用意し、公開URLから取得できること、スキーマに通ることを確認しました。そのうえで、本番のブラウザで群馬県・北海道・東京都の学校を開き、タイトル、表紙、購入リンクが各県のJSONと一致することを確認しています。対象外の私立高校で広告が出ないことも確認しました。

ここで確かめたのは、取得と表示の経路です。アフィリエイトの成果計上や、すべての実端末での動作まで確認した、という意味ではありません。

広告ブランチへのpushでPagesのアプリビルドが走らないことも確認し、v0.12.0として公開しました。初回は読み込み機構を入れるのでアプリのリリースが必要です。そこを越えた後は、同じ形式の広告データだけを独立して更新できます。

楽天APIなどで候補を取得する自動化は、今後の検討です。今回作ったのは、選んだ商品を県別のJSONにして、安全に読み込むところまで。商品を選ぶ仕組みと、選んだ商品を届ける仕組みを分けておけば、後から取得方法を変える余地も残ります。

小さな広告枠でも、コードと一緒に更新するものなのか、データとして更新するものなのかを決めると、運用が変わりました。今回は、商品を差し替える作業がGitHubのJSON更新で済むところを、まず作っています。

## manabi-mapについて

manabi-mapは「通える高校を地図で見ながら、親子で決める。」を目指して作っているWebアプリです。

- 地図で学校の位置と通える範囲を見ながら探せます。
- 気になる学校を比較し、検討した内容をメモできます。
- 根拠を確認できる情報をもとに、進路選びを進められます。

[アプリを開く](https://manabi-map.app)から利用できます。[作品紹介](https://ishizakahiroshi.com/work.html?id=manabi-map)と[GitHubリポジトリ](https://github.com/ishizakahiroshi/manabi-map)も公開しています。役に立ちそうでしたら、GitHubのStarで応援してもらえるとうれしいです。

![フリーズを記録し、調査の仕込みを出荷前に外す](/images/01_2026-09-27_freeze-purge_hero.png)

音声入力の途中で、Webの管理画面が固まりました。ボタンも効きません。でも、新しくタブを開くと普通に動きます。

UIフリーズを次に捕まえるため、Web Workerでデバッグログを残す仕組みを足しました。同時に決めたのが、**調査用に仕込む機能は、リリース前にパージする**ことです。

この記事は原因を解決した報告ではありません。観測の準備と、出荷前に外す仕組みを作り、最後の点検で取りこぼしも見つかったところまでの記録です。

題材は自作の many-ai-cli です。複数の AI コーディング CLI を並列で走らせ、承認をブラウザ 1 タブに集約。スマホからでも。

- [何ができるかの紹介ページ](https://ishizakahiroshi.com/work.html?id=many-ai-cli)
- [リポジトリ。Starをいただけると励みになります](https://github.com/ishizakahiroshi/many-ai-cli)

## 「あとで消す」を、リリースの条件にしました

先に、今回の実装で使うコマンドを置きます。リポジトリのルートで実行します。

```sh
# 調査中の通常チェック
node scripts/check-instrumentation.mjs

# リリース前。未パージの調査機能があれば失敗する
node scripts/check-instrumentation.mjs --release

# 調査を終え、対象の専用実装をまとめて外す
make debug-purge id=ui-freeze-recorder
```

最後のコマンドは診断実装を削除するので、これから観測する段階では実行しません。現在は調査機能を `active` として残しており、リリース検査が失敗する状態が期待どおりです。

「普段はOFF」「リリースビルドでは読み込まない」だけで終わらせたくありませんでした。調査のために足したWorker、保存API、登録処理、専用テストをひとまとまりで管理し、調査が済んだら同じ単位で外します。

この作業を、ここではパージと呼んでいます。ログファイルの掃除とは別の話です。

## 新しいタブが動いても、原因はまだ分かりません

固まった画面では、音声入力もほかの操作も反応しません。新しいタブは動くので、Hub全体が停止したと即断する材料にはなりませんでした。

では、止まったタブを後から調べればいいか。今回は、そのタブへのブラウザ調査操作自体がタイムアウトしました。見たいときには見えない。ここが困ります。

調査中には、リンク検出で使う正規表現にも別の問題が見つかりました。末尾の記号を取り除く処理が、特定の合成入力で長時間戻ってこなくなります。ここは線形の走査に直し、旧実装との差分もテストしました。

ただし、それで音声入力中のフリーズ原因が確定したわけではありません。遅くなるコードを見つけたことと、目の前の停止を説明できたことは分けておきます。

次の再発で手がかりを残すために、事前の記録を用意することにしました。

## 画面と一緒に、記録係まで止まると困ります

画面側でタイマーを回し、そこからログを送るだけだと、画面のJavaScriptが詰まったときに記録も止まります。

今回は、画面から専用のWeb Workerへ定期的な生存通知を送り、Worker側からHubへ記録を保存する形にしました。Web Workerはページのメインスレッドとは別にスクリプトを実行でき、メッセージでやり取りします。[MDNのWeb Workers解説](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)

![止まった装置の隣で記録を続ける別の装置](/images/03_2026-09-27_freeze-purge_illustration-recorder.png)

画面の仕事と記録の仕事を分け、画面から連絡が来なくなったことを別の場所で拾います。ただし、ブラウザやOS全体が止まればWorkerも動けません。

記録点は、音声認識結果の反映、入力欄のサイズ計算、端末サイズの調整、リンク検出の4か所です。それぞれの同期処理について、開始と終了を送ります。

コードの形は次のようになります。説明用に単純化した例です。

```ts
const finish = probeSpan('ui-freeze', () => ({
  phase: 'input.layout',
  length: input.value.length,
}));
try {
  resizeInput();
} finally {
  finish?.();
}
```

開始はあるのに終了がない記録が残れば、その処理の周辺から調べられます。これはスタックトレースではなく、最後に通った場所を絞るための手がかりです。

前面のタブから5秒以上生存通知が来なければ、停止の疑いとして記録します。復帰と、Worker自身の実行間隔が大きく空いた場合も分けました。スリープやタイマーの遅れを、すべて同じ「フリーズ」にまとめないためです。

## 発話の本文を集めなくても、記録できることはあります

欲しいのは「何を話したか」より、「どこまで処理が進んだか」です。

今回の診断ログには、処理の種類、開始と終了、時刻、文字数などを記録します。発話本文、端末本文、認証値は送りません。タブを区別するための識別子は持ちます。

直近のイベントは64件、終了を待っている処理は16件に制限しました。送信は同時に1件まで。タイムアウトと再試行の間隔も設け、観測の仕組みが通信やメモリを膨らませないようにしています。

Hub側では専用のJSONLへ保存します。通常ログの設定に依存させず、1ファイル1MB、バックアップ2個という上限を置きました。保存先のAPIも既存の認証やOrigin検査を通します。[保存APIの実装](https://github.com/ishizakahiroshi/many-ai-cli/blob/6dd1a98dedbc7b29e8e671816fb8ae533e0180ee/internal/hub/debug_ui_freeze.go)

こういう制限は、ログを仕込んだ直後に決めておきたいです。フリーズを調べる道具で、別の重さを増やすのは避けたいので。

## 専用の実装と、共有コードの記録点を分けます

今回の主な構成はこうです。

```text
instrumentation.json               調査機能の台帳
scripts/check-instrumentation.mjs   検査・パージ
web/src/debug/
  probe.ts                        共有の記録窓口
  ui-freeze.ts                    今回専用のWorkerと記録処理
internal/hub/
  debug_ui_freeze.go               今回専用の保存API
```

台帳には、専用ファイル、共有ファイル、登録先、成果物から検出する文字列、状態、撤去期限を持たせます。

共有コードには薄い記録点を置き、記録先がなければ何もしない形にしました。パージでは専用実装と登録を取り除き、共有の窓口は残します。**何も記録しない窓口と、実際に記録・保存する調査機能を区別する**ためです。

![調査中の登録からパージ、リリース検査へ進む流れ](/images/04_2026-09-27_freeze-purge_fig1.png)

通常の検査は調査中の開発を許し、リリース用の検査は未撤去の項目を拒否します。パージを独立したコミットにすれば、必要になったときに既存の復元手順で戻せます。

ビルド側にも分離があります。Web側はデバッグ指定、Go側は `maidebug` のビルドタグを使います。ただし、非同梱の指定があることだけで「パージ済み」とは扱いません。

リリースの事前検査は、台帳の全項目が `removed` であることを要求します。「今回は期限内だから出していい」という例外も作りませんでした。[今回の実装差分](https://github.com/ishizakahiroshi/many-ai-cli/commit/6dd1a98dedbc7b29e8e671816fb8ae533e0180ee)

## テストが通ったあとに、取りこぼしが見つかりました

Workerのテストでは、親のイベントループを6.5秒止めている間に、別のWorkerが停止疑いの記録を残すことを確認しました。ただし、Nodeの `worker_threads` を使うアダプタと保存用スタブでの検証です。実ブラウザの音声入力、Cookie、CSPを一緒に通した試験ではありません。

Go側では保存APIと入力制限を別に検証しました。隔離した一時リポジトリでは、通常検査が通る、リリース検査が落ちる、実際にパージすると通る、という一連の動きもテストしています。

このテスト中に、台帳を `removed` にしても未追跡の専用ファイルが残っていると見逃す穴が見つかりました。ここは、Gitの追跡状態によらずファイルの存在を見るように直しました。コミット後の[Validate CIも成功](https://github.com/ishizakahiroshi/many-ai-cli/actions/runs/36269549604)しています。

それで終わりにせず、「現行の仕込みがまだ紛れていないか」を追加で点検しました。

ありました。

- 承認画面の表示・非表示を追う、台帳外の `console.log`。質問文や選択肢の一部、スタックも出していました。
- 表示崩れの再発調査用に追加された、端末サイズ変更の履歴。通常ビルドにも実装が残り、セッション履歴を有効にすると保存される形でした。

前者の識別文字列は、手元に残っていた既存のWeb成果物と実行ファイルにもありました。ただし、これは今回のコミットから作り直した成果物ではありません。公開済み配布物を検査した結果でもありません。

それでも、既知の文字列を探す成果物検査は通りました。検出対象のリストに、その文字列がなかったからです。

![登録された検出語だけでは、未登録の追跡は拾えない](/images/05_2026-09-27_freeze-purge_fig2.png)

検査が答えたのは「知っている文字列は見つからない」まででした。未登録の追跡がないことまでは、答えられません。

## まだ残っている仕事も、記事に残しておきます

執筆時点では、実機への新しい診断コードの反映と、再発時の記録回収はこれからです。フリーズの原因も未確定です。

追加点検で見つかった台帳外の2系統は、まだ是正していません。また、リリース手順には成果物検査が公開処理の後にある箇所があり、成果物の混入を公開前に止める順序へ直す必要があります。今回追加した、台帳に基づくソースのパージ検査は公開前に動きます。

通常のエラーログや、製品として用意している音声の診断機能まで、一律に取り除く話ではありません。一時調査の仕込みなのか、利用者を支える機能なのかを確認してから扱います。

今回できたのは、観測の道具と撤去の経路、それから取りこぼしの具体的な一覧です。「全部きれいになった」とは、まだ書けません。

## many-ai-cli はこんなときに使えます

- 複数のAIコーディングCLIを同時に動かし、状態を1画面で見たい人
- あちこちのターミナルを往復せず、承認待ちをまとめて確認したい人
- 離席中もスマホから承認したい人

通常版を試す手順は[READMEの初回起動案内](https://github.com/ishizakahiroshi/many-ai-cli/blob/develop/README.ja.md)にあります。

```sh
npm install -g many-ai-cli
many-ai-cli setup
```

Windowsでは作成された「MANY-AI-CLI」ショートカットからトレイを起動し、「Hubを開く」を使います。停止もトレイの「Hubを停止」からできます。macOSとLinuxでは「Many AI Hub Start」「Many AI Hub Stop」を使います。

ターミナルからは `many-ai-cli serve --open` で起動し、別のターミナルから `many-ai-cli stop` で止められます。起動後はダッシュボードからCLIのセッションを作ります。macOSとLinuxのネイティブ環境は、README上で実機の十分な検証が未完了とされています。

このインストール手順で今回の調査用コードが有効になるわけではありません。

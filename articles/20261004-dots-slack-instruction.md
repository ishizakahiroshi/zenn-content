## 入口を二つにしても、依頼の置き場所は揃える

私の環境では、ChatGPTとClaude Codeの両方からSlackへ投稿し、dotsに作業を依頼しています。この記事でいうdotsは、Slackで話しかけられ、許可されたGitHubリポジトリを読み、別の実行環境で作業してbranchやPRを返すAIエージェントです。これは手元で利用している構成の説明で、一般の提供条件や内部構成を説明するものではありません。

接続ができるだけでは、複数の仕事を追い続けるには足りません。どの依頼の続きか、何を読んだか、どこまで終わったかを毎回会話から推測する形では、入口を増やすほど確認が難しくなります。

そこで、案件番号、GitHubの固定commitに置く指示書、対象repoのPROGRESS.mdという看板、Slackの同じスレッドを揃えました。ChatGPTかClaudeかは依頼を整理して届ける入口です。作業の基準と成果の置き場所を共通にすることで、途中から別のAIで状況を聞く場合にも、同じ案件を指せるようにしています。

![二つの窓口から一つの会話を通して依頼が届く、文字のない挿絵](/images/03_2026-10-04_dots-slack-instruction_illustration.png)

## 指示は固定し、進捗は更新する

最初に、手元の採番台帳から案件番号を取ります。同じrepoと同じ案件keyなら同じ番号を使い、番号は再利用しません。GitHubのIssue番号やPR番号とは別の識別子です。実際に短い番号を依頼の頭に付けてからは、続きの会話でもその番号で仕事を指せました。

次に、対象repoに次のファイルを用意します。パスは構成例です。

```text
docs/bot/<task-slug>/
  README.md    目的・範囲・禁止事項・提出先・完了条件
  REVIEW.md    実装者とは別の担当が確かめる観点
  PROGRESS.md  工程・担当・状態・証跡・次の一手
```

README.mdには、触ってよい範囲と、進めてはいけないところを両方書きます。たとえば「このディレクトリの文書だけ」「成果branchを作る」「mergeや公開は手元」という具合です。完了条件も「ファイルを作る」だけで終わらせず、提出する形式、確認方法、誰が検収するかまで揃えます。

指示書をpushしたら、そのcommitのURLを渡します。branchの最新版だけを指すと、依頼した時点と後から開いた時点で内容が違う可能性があります。受け手が読んだcommitを受付で返せば、こちらの想定する版と照合できます。途中で要件を変える場合も、差分と新しい基準を同じ会話に残します。

一方、PROGRESS.mdは変化を見るための看板です。こちらは成果branchの最新版を追います。固定する指示と更新する状況の役割を分けておくと、古い要件を知らないうちに上書きしたり、古い進捗を最新と取り違えたりするのを避けやすくなります。

## Slackは短い依頼と受付の確認に使う

SlackのDMでは「#番号 案件名」で親メッセージを立て、その後は同じスレッドを使います。本文は、番号、対象repo、固定指示URL、看板URL、作業範囲、提出先、受付で返してほしいことに絞ります。長い仕様を複数のチャットにコピーするより、指示書を参照してもらう形です。

受付では、少なくとも次を確認します。

- 同じ番号の別案件がないか
- どの固定commitを読んだか
- 必要な言語、依存取得、ブラウザなどを実際に使えるか
- 何をどのbranchへ提出するか
- 進められない工程があれば、その工程と再開に必要なもの

ここで「送れた」と「受け付けられた」を分けます。送信結果のリンクや本文を読み戻せても、作業者が指示を理解し着手した証拠にはなりません。受付の返信まで確かめます。同様に、受付があってもテスト成功を意味しません。

私の運用ではdotsの返信は依頼のスレッドに付きました。トップレベルの履歴だけを見て、返事がないと判断しないようにしています。状況を聞くときは番号に加えてrepoや該当Issueを指定すると、確認対象を絞れます。別の入口から送るときも、新しい案件を立て直さず、同じ番号と会話を渡します。

## ChatGPTからSlackへ接続する

公式ヘルプに沿って、ChatGPTから接続したSlackを使う経路を設定します。Slack内で@ChatGPTに話しかける経路とは異なります。過去に私が操作した画面の記録はないため、以下は現在の公式案内と、送信を確かめるための手順です。[経路の違い](https://help.openai.com/en/articles/20001536-chatgpt-with-slack-and-microsoft-teams)

1. ChatGPTの設定で「Plugins」、画面によっては「Apps」を開き、Slackを選びます。「Install plugin」がある場合は内容を確認して導入し、「Connect」へ進みます。[接続手順](https://help.openai.com/en/articles/20001494-connecting-and-managing-app-accounts-in-chatgpt)
2. 投稿に使う本人のSlackアカウントと、dotsとのDMがあるワークスペースを選び、要求権限を確認して認可します。管理された環境ではSlackと必要なアクションが有効かも確認します。Slack側のポリシーにより、管理者承認や追加スコープの再認可が必要になる場合があります。[Slackの設定と権限](https://help.openai.com/en/articles/12525822-using-slack-in-chatgpt)
3. ChatGPTの会話で、必要なら「@」や「＋」からSlackを指定します。自分宛てDMへ「ChatGPTからの送信テスト」を1通送るよう依頼し、確認画面が出たら宛先と本文を確認します。[会話での使い方](https://help.openai.com/en/articles/20001494-connecting-and-managing-app-accounts-in-chatgpt)
4. 返されたリンクを開いて本文と投稿者を見て、ChatGPTにも読み戻してもらいます。その後、既に利用できるdotsとのDMへ1通送り、投稿のスレッドで返答を読みます。この順序は本記事で提案する動作確認です。

接続済みや検索成功だけで、投稿可能とは判断しません。私の環境では本人名義で送れましたが、読者の契約や組織で同じアクションが使えることまでは保証できません。

## Claude CodeからSlackへ接続する

Claude Code CLIが使え、対象Slackで連携が許可されていることを前提に、動作を確認できた公式MCPプラグインを使います。[Slack公式の前提条件](https://docs.slack.dev/ai/slack-mcp-server/connect-to-claude/)

1. 端末で `claude plugin install slack` を実行します。これは私が使ったコマンドで、Slack公式にも掲載されています。接続先は公式MCPサーバー `https://mcp.slack.com/mcp` です。[導入手順](https://docs.slack.dev/ai/slack-mcp-server/connect-to-claude/)
2. 導入後のClaude Codeで `/mcp` を開き、Slackサーバーを選んでOAuth認証を進めます。ブラウザでアカウント、ワークスペース、権限を確認します。私の画面では `plugin:slack:slack` と表示されました。[MCP認証](https://code.claude.com/docs/en/mcp)
3. 接続と利用できるツールを確認します。私の試行では認証前から開いたセッションにツールが出ず、新しいセッションで使えました。公式には新しい起動や `/reload-plugins` による読み込みが案内されています。[プラグインの反映](https://code.claude.com/docs/en/discover-plugins)
4. 自分宛てDMへ1通送り、リンクと読み戻した本文を照合します。次に既に使えるdotsとのDMへ1通送り、返信スレッドを読みます。Slack MCPは送信と履歴・スレッド読み取りを提供しますが、使える範囲は認可に従います。[MCPの機能](https://docs.slack.dev/ai/slack-mcp-server/)

提供元まで明記する別の導入方法は、セッション内の `/plugin install slack@claude-plugins-official` です。どちらか一方の方法で導入します。[現在の公式プラグイン](https://docs.slack.dev/ai/slack-skills-plugin/)

私の試行では追加の管理者承認は出ませんでした。ただし、必要な承認は各ワークスペースのポリシーや承認済みの範囲によって異なります。[Slackのアプリ承認](https://slack.com/help/articles/202035138-Add-apps-to-your-Slack-workspace)

最初に試したclaude.aiのSlackコネクタは、私の環境ではClaude Codeに現れず、原因は未特定です。公式にはclaude.aiのMCP接続を使う経路もあります。一般的に使えない仕様とはせず、今回は動作したプラグイン経路を紹介しています。[公式の接続説明](https://code.claude.com/docs/en/mcp#use-mcp-servers-from-claudeai)

## 看板と外側の監視で、次に聞くことを決める

作業中は、工程、担当、状態、証跡、次の一手をPROGRESS.mdに残してもらいます。「進行中」だけでは判断材料が少ないので、成果commit、試したコマンドと結果、CI、確認できなかった範囲を添えます。失敗した試行も、方法と再開地点が残っていれば引き継ぎに使えます。

さらに私は、別の非公開repoに読み取り専用の監視スクリプトを置いています。見るのはGitHub側のbranchの進み、PRとCI、対象ラベルのIssue、直近の取り込み時刻などです。対象repoの看板を別の場所へ集約して置き換えるのではなく、外側から変化を確かめる補助にしています。

この監視では既定60分、変化のないrepoを「停滞」として出します。ただし、60分は私が選んだ運用上の値です。エージェントの処理時間や応答を保証する数字ではありません。GitHubの更新がないことだけから、仕事が止まった理由は分かりません。

停滞が出たら、先にbranch、PR、CIの事実を見てから、同じ案件のスレッドで聞きます。承認待ち、環境の制限、依存の取得失敗、仕事が大きすぎる場合を同じ「待ち」にしないためです。監視から自動で再実行やmergeを行うことはありません。

dotsの環境で依存パッケージを取得できず、手元でそこだけ補った仕事もありました。大きなIssueで2時間以上PRが出なかったこともあります。それを一般的な性能評価にはせず、いまは30〜60分を目安に区切れる単位へ依頼を分ける方針にしています。

## 完了報告の次に、独立して受け取る

成果が届いたら、報告されたcommitを固定してレビューします。実装した担当とは別の担当が指示と差分を照合し、私の手元でも必要な確認をします。Windows実機、実際の画面、本番に関わる確認は、別環境でのテスト成功から推測しません。

「原稿提出」「独立レビュー」「手元検収」「公開」「公開画面の確認」は別々の状態です。この記事でも本文と5画像の制作はdotsの担当ですが、Zenn、Qiita、noteへの投稿と実URLでの表示確認は手元の担当にしています。投稿用認証や投稿先repoへのpushを依頼に含めていません。

この区切りがあると、失敗した一工程だけを修復し、その先へ戻しやすくなります。認証値やCookie、生ログを会話に貼って解決しようとはしません。権限が必要な場合は、対象と操作を特定して確認し、同じ承認で無関係な作業まで進めないようにします。

まだ、停滞の理由を外から自動判別できるわけではありませんし、手元検収も残ります。それでも、誰が何を確認するかと、次に参照する場所は揃えられます。これから同じ形を作るなら、小さい一件で接続、送信、受付、成果、検収を順に通し、そこで足りなかった証跡を指示書へ戻すところから始めるのがよさそうです。
